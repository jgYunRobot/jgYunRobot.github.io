로봇을 직접 연결하다 보면 입력 장치, 로봇 모델, 통신 방식이 서로 다른 속도로 바뀐다. 처음에는 리더 암을 읽어 관절 목표를 보내지만, 다음에는 카메라 관측을 읽은 정책이 목표를 만들게 된다. 제어 대상도 학습용 로봇에서 EtherCAT으로 연결한 로봇으로 바뀐다.

개인 프로젝트 **Nodus**에서는 이런 변화가 생기는 지점을 기준으로 역할을 나누고 있다. 이 글은 2026년 10월 기준 구조를 정리한 기록이다.

## 목차

## 무엇을 분리했나

| 구성          | 담당하는 일                                                      | 변경의 예                   |
| ------------- | ---------------------------------------------------------------- | --------------------------- |
| nodus_rm      | 로봇 모델, 기구학·동역학, Jacobian, 경로·시간 계획에 필요한 연산 | 기구 구조나 제어점 변경     |
| nodus-control | Task 구성, 모션 목표, 제어 연산과 관절 명령 계산                 | 제어 알고리즘·제약 변경     |
| nodus-pilot   | 상위 입력·정책 실행, 카메라·기록 연계, 명령 라우팅과 상태 제공   | 입력 앱·정책·관측 장치 변경 |
| Robot Adapter | 공통 관절 상태·명령과 장치별 패킷 사이 변환                      | EtherCAT·Serial 장치 변경   |

Pilot은 모션 명령을 전달하는 역할만 담당하지 않는다. 입력과 정책을 실행하고, 상태를 관측하며, 카메라와 기록 기능을 연결하는 상위 실행 계층이기도 하다. 반면 로봇 연산과 주기 제어는 독립된 라이브러리의 책임으로 유지한다.

## 명령과 관측은 다른 방향으로 흐른다

다음은 책임을 설명하기 위한 개념 흐름이다. 실제 함수 호출 순서를 그대로 나열한 것은 아니다.

```text
Operator / Teleoperation / Policy
              │ 목표
              ▼
            Pilot
              │ 명령 라우팅
              ▼
           Control ◄── 모델·연산: nodus_rm
              │ 관절 명령
              ▼
         Robot Adapter
              │
              ▼
             Robot

로봇 상태는 반대 방향으로 돌아와 관측·화면·기록에 사용된다.
```

센서 데이터도 별도로 생각해야 한다. 카메라나 센서의 payload를 Pilot이 전부 중계하는 구조로 만들기보다, Provider와 Consumer가 연결될 수 있는 등록·탐색 경계를 두었다. 명령, 상태, 영상이 같은 생명주기와 전달 특성을 가진다고 가정하지 않기 위해서다.

## 목표를 표현하는 단위는 Frame

관절 번호만으로 목표를 지정하면 TCP가 바뀌거나 양팔을 구성할 때 상위 코드가 기구 구조를 많이 알아야 한다. Frame을 제어점과 기준으로 사용하면, 입력 쪽에서는 무엇을 어느 기준에서 움직일지 표현하고 제어 쪽에서 이를 모델과 연결할 수 있다.

다만 Frame이 존재한다는 사실과 해당 Frame을 관절이 움직일 수 있다는 사실은 다르다. 모델에서 조회할 수 있는 대상인지, 실제 제어에 필요한 관절 연결을 가진 대상인지를 구분해야 한다.

## API 응답이 곧 동작 완료는 아니다

명령 접수, 제어 계층으로 전달, 처리 결과 수신, 물리적인 운동 완료는 서로 다른 상태다. 상위 앱에서 HTTP 요청이 성공했다고 로봇이 목표에 도달했다고 해석하면, 다음 작업의 시작 조건이 틀어질 수 있다.

이 구분은 통신 패킷 형식보다 먼저 정해야 하는 계약에 가깝다. 제어기의 내부 구현을 바꾸더라도 상위 앱에서 상태의 의미를 일관되게 읽을 수 있어야 한다.
